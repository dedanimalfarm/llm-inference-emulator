# LLM FinOps: когда окупается собственное железо?

До сих пор мы говорили о *физике* инференса — флопсах, байтах и секундах. Но в реальном мире секунды стоят денег. Главный вопрос, который встает перед любым проектом, использующим LLM: **«Использовать Managed API (по токенам), арендовать GPU почасово (Cloud) или купить собственные серверы (On-Premise)?»**

Давайте применим нашу roofline-модель и актуальные цены на API (например, с агрегатора OpenRouter) и облачные GPU, чтобы рассчитать экономику математически и разобрать реальные бизнес-сценарии.

## 1. Базовые расценки (Начало 2025)

Цены на open-source модели переживают «гонку на дно». Провайдеры (Groq, Together, DeepSeek) субсидируют инференс, работая на гигантских масштабах. Типичные цены за 1 миллион токенов (среднее между prefill и decode):
*   **Класс 8B** (Llama-3.1-8B): ~**$0.05** за 1M токенов.
*   **Класс 70B** (Llama-3.1-70B): ~**$0.40** за 1M токенов.
*   **Класс 400B+** (Llama-3.1-405B): ~**$3.00** за 1M токенов.

Аренда GPU (serverless / почасовая, например RunPod, Lambda Labs):
*   **1× RTX 3090 / RTX 4090**: ~$0.40 в час.
*   **1× A100 80GB**: ~$1.50 в час.
*   **8× H100**: ~$25.00 в час.

## 2. Вариант A: Использование Managed API (Оплата за токены)

**Реальные сценарии использования:**
1. **MVP и проверка гипотез.** Стартап пилит приложение-помощника. Аудитории еще нет, трафик нулевой. Платить $400/мес за аренду сервера ради 10 запросов в день — финансовое самоубийство.
2. **Нерегулярная нагрузка (Spiky Traffic).** B2C-приложение (например, Telegram-бот для студентов). Во время сессии миллион запросов, летом — ноль. API берет всю головную боль по балансировке нагрузки на себя.
3. **Отсутствие DevOps/MLOps экспертизы.** Команда состоит из frontend-разработчиков и product-менеджера. Поднимать свой vLLM, бороться с CUDA-драйверами, настраивать PagedAttention и следить за падениями GPU — слишком дорого (зарплата MLOps инженера перекроет любую экономию на токенах).
4. **Agentic Workflows (SGLang/LangChain).** Когда агенты делают десятки коротких вызовов-размышлений, скорость получения первого токена (TTFT) и memory-bound decode на мощнейших кластерах API-провайдеров критически важны для UX.

> **Кейс из индустрии (Переход с API на Open Source):** Платформа для медицинских ИИ-агентов **Sully.ai** начинала с использования проприетарных API (GPT-4). По мере роста объема специализированных задач (генерация медицинских карт) стоимость API стала блокировать рост. Переход на собственные инстансы с оптимизированными open-source моделями (Llama 3 на Nvidia Blackwell) снизил их затраты на инференс на **90% (в 10 раз)** и ускорил ответы на 65%.
> 
> *Золотое правило от a16z («Navigating the High Cost of AI Compute»):* Начинайте с API, чтобы найти product-market fit. Переходите на собственное железо/Cloud GPU только для тех задач, которые генерируют основной объем токенов (обычно порог рентабельности начинается от 10+ млн токенов в месяц).

**Математика (Сценарий Исследователя):**
Исследователь или небольшая команда анализирует документы с помощью **Llama-3.1-70B**. 
Нагрузка: 50,000 токенов промптов и 10,000 токенов ответов каждый день. Итого ~1.8 миллиона токенов в месяц.
*   **Затраты на API:** 1.8M токенов × $0.40 = **$0.72 в месяц**.

> **Вывод:** При низком батче (memory-bound) API всегда на порядки дешевле. Вы не платите за простой (idle) мощного чипа. Свое железо здесь берут только ради privacy (нельзя отправлять данные в API) или для uncensored генерации.

## 3. Вариант B: Почасовая аренда (Cloud GPU)

**Реальные сценарии использования:**
1. **Корпоративный инструмент в рабочие часы.** Внутренний RAG-бот компании или ассистент поддержки. Трафик высокий, батчи собираются, но **только с 9:00 до 18:00 (5 дней в неделю)**. Ночью и в выходные трафика нет. Вы динамически поднимаете инстанс (auto-scaling) утром и убиваете вечером.
2. **Ночные пакетные обработки (Batch Processing).** Финтех-стартап каждую ночь загружает 100,000 новостных статей, чтобы извлечь из них сущности (NER) и сентимент. Ровно в 00:00 поднимается кластер из 10 GPU, модель переходит в жесткий compute-bound (batch=100+), перемалывает данные за 3 часа и выключается.
3. **Finetuning / Обучение.** API не позволяет дообучать модели (или это стоит несоразмерно дорого). Вы арендуете H100 на 10 часов, прогоняете датасет через LoRA и сохраняете веса.
4. **Асинхронные задачи на Spot-инстансах.** Анализ огромных логов, где сбой машины не критичен. Облачные провайдеры (AWS, GCP) отдают прерываемые GPU со скидкой **60–80%** (3x-6x дешевле on-demand).

> **Кейс из индустрии (Оркестрация Spot-инстансов):** Использование фреймворков вроде **SkyPilot** или **SpotServe** позволяет автоматически искать самые дешевые Spot-инстансы по всем регионам и облакам. Если AWS забирает ваш GPU (дает 2-минутный preemption warning), оркестратор ставит ноду на паузу и прозрачно поднимает новую в другом регионе. Это позволяет крутить LLM-инференс за ~$400/мес вместо ~$1200/мес (on-demand).

**Математика (Корпоративный RAG):**
*   Для 70B (INT4) вы арендуете 2× RTX 3090 на 9 часов в день: 9 × $0.60 = **$5.4 в день** (~$118 в рабочий месяц).
*   Это выгоднее, чем держать On-Premise сервер включенным (или окупать его Capex при простое 15 часов в сутки и все выходные).
*   API в этом сценарии все еще может быть дешевле, если суммарный объем токенов за эти 9 часов не превышает $\approx 13$ миллионов.

> **Вывод:** Cloud GPU идеален для предсказуемо-рваной нагрузки (рабочие часы) или мощных фоновых задач (nightly batches). Вы получаете полный контроль над моделью, но не платите за железо, когда оно простаивает.

## 4. Вариант C: Покупка собственного железа (On-Premise)

**Реальные сценарии использования:**
1. **Успешный B2B SaaS с высокой нагрузкой 24/7.** Вашим сервисом пользуются клиенты в разных часовых поясах. Сервер постоянно держит батч $b \ge 25$. Модель находится в `compute-bound` режиме (FLOPs утилизируются на 100%).
2. **Жесткие требования к безопасности (Compliance, NDA, Healthcare, Defense).** Данные клиентов (медицинские карты, банковские транзакции) физически не имеют права покидать контур компании. API использовать запрещено законом. Облако требует сложных договоров (BAA). Проще и безопаснее поставить сервер в свою закрытую стойку.
3. **Специфические Uncensored / Custom модели.** Вы используете сильно модифицированную или NSFW-модель, которую не хостят публичные API. 
4. **Реалтайм аналитика (Ультра-низкая задержка / HFT).** Биржевые алгоритмы, голосовые роботы (Voice AI), управление робототехникой. Сетевой прыжок до API-провайдера и обратно добавляет 50–150 мс задержки. Если модель крутится на видеокарте в соседнем PCIe-слоте сервера обработки, сетевая задержка физически равна нулю.

> **Кейс из индустрии (A16z: AI is Compute-Bound):** Согласно исследованию a16z, многие ИИ-стартапы на ранних стадиях тратят **более 80% привлеченного капитала** на вычислительные мощности. AI-компании экономически ближе к капиталоемким инфраструктурным проектам, чем к традиционному SaaS. Если ваши траты на облачный AI-compute превышают **$50 млн в год**, финансово целесообразно строить собственный on-premise датацентр.

**Математика (B2B Сервис 24/7):**
Давайте посчитаем экономику сервера с **2× RTX 3090** (48 ГБ VRAM), на котором мы крутим **Llama-3.1-70B (INT4)** под управлением vLLM.
*   По формуле из Части 4, пропускная способность сервера с 2× RTX 3090 (TP=2) в compute-bound режиме достигает **~400 токенов/с**. 
*   При круглосуточной работе это **34.5 млн токенов в сутки**.
*   **Стоимость API:** 34.5M × $0.40 = **$13.8 в день** ($414 в месяц).
*   **Стоимость аренды Cloud GPU 24/7:** $0.60/час × 24 = **$14.4 в день** ($432 в месяц).
*   **Стоимость On-Premise:** Capex: **$2600**. Opex (электричество 24/7): **$3 в день** ($90 в месяц).
*   Чистая экономия On-Premise относительно API: $13.8 - $3 = **$10.8 в день**.

**Срок окупаемости железа:** $2600 / $10.8 = **240 дней (8 месяцев)**.

> **Вывод:** При постоянной нагрузке 24/7 и утилизации близкой к 100% покупка железа окупается меньше чем за год. Если нагрузка падает (средняя утилизация 30%), окупаемость растягивается до 2–3 лет.

## 5. Вариант D: Edge & On-Device (Inference на конечных устройствах)

**Реальные сценарии использования:**
1. **IoT и Автономные системы.** Дроны, умные камеры, автомобили, робототехника на производствах. Подключение к сети может быть нестабильным или отсутствовать, а API недоступно. Модель должна работать локально (Offline mode) с гарантированным нулевым временем отклика по сети.
2. **Мобильные приложения (Smartphones).** Apple Intelligence, локальные LLM на Android (через MLC LLM, MediaPipe). Инференс происходит прямо на NPU телефона пользователя.
3. **Consumer Software.** Локальные ИИ-помощники в IDE или десктопном софте (например, на корпоративных макбуках разработчиков в air-gapped среде без доступа к интернету).

**Экономика (FinOps):** Это святой Грааль для B2C сервисов. Вы переносите Capex (стоимость кремния) и Opex (электричество) на плечи конечного пользователя устройства. Инференс для вашей компании становится абсолютно бесплатным ($0 / токен). Главное ограничение — жесткий лимит на размер модели (обычно 1B–8B параметров и агрессивное квантование INT4/INT3).

## 6. Гибридная архитектура (Cloud Bursting)

В Enterprise-мире редко выбирают только один путь. Самый эффективный FinOps-паттерн — **Гибридный**:

1. Вы покупаете **On-Premise** серверы (или арендуете Cloud GPU по долгосрочным Reserve-контрактам со скидкой) ровно на тот объем, который покрывает ваш *базовый (минимальный) круглосуточный трафик*. Это гарантирует 100% утилизацию железа и минимальную стоимость за токен (compute-bound).
2. Когда случается **пик трафика (Spike)**, который железо не может переварить (загрузка GPU 100%, очередь растет), ваш LLM-балансировщик (например, **LiteLLM**, **Martian** или **Cloudflare AI Gateway**) прозрачно перенаправляет излишки запросов в **Managed API** (OpenRouter, Groq, OpenAI).
3. Вы платите дорогую ставку API *только* за излишки, избегая покупки лишних серверов, которые простаивали бы 90% времени в ожидании пиков.

## 7. Дает ли свое железо преимущество по скорости?

Частый вопрос: *«Если я куплю свой сервер (или арендую инстанс), будет ли модель отвечать быстрее, чем по API?»*

**Ответ: Для одного запроса — нет. Для пропускной способности — да.**

1. **Скорость одного ответа (TTFT и Decode Speed).** Провайдеры API (Groq, Together) обслуживают Llama-70B на кластерах из **8× H100**, используя массивный Tensor Parallelism (TP=8). Это дает гигантскую эффективную пропускную способность памяти ($B_{\text{eff}}$) и невероятно быстрый memory-bound decode. Вы на своих 2× RTX 3090 никогда не получите скорость генерации в 100+ токенов/с для одного пользователя, которую дают гиганты.
2. **Гарантированная задержка (Predictability).** Публичное API подвержено сетевым задержкам, rate limits (лимитам запросов) и эффекту «шумных соседей» (вечером API может тормозить). Свой сервер (Cloud или On-Premise) дает 100% стабильный TTFT и никаких лимитов.
3. **Throughput per dollar.** Свое железо выигрывает не в скорости ответа одному пользователю (стриминге), а в количестве пользователей, которых можно обслуживать одновременно за те же деньги, если перейти в compute-bound (batching).

## Главное правило LLM FinOps

1. **Memory-bound (Batch ≈ 1):** Вы переплачиваете за простой (idle) мощнейшего чипа. **API всегда дешевле**. Свое железо нужно только для NDA/приватности.
2. **Compute-bound (Batch = 20+):** Вы выжимаете из кремния все FLOPs. 
    * Если нагрузка 24/7 — **покупка железа (On-Premise) выгоднее всего**.
    * Если нагрузка «рваная» или только в рабочие часы — **почасовая аренда (Cloud GPU) с автоскейлингом оптимальна**.
3. **Скорость:** Если нужна минимальная задержка (latency) для *одного* потока — API на H100 непобедимы. Если нужна стабильность, независимость от rate-лимитов и максимальный throughput — поднимайте свои инстансы.
